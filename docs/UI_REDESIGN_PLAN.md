# แผนออกแบบ benzPOS ใหม่ — แยกสาขาตามสิทธิ์

ปรับปรุง 7 กันยายน 2026 · ใช้รายชื่อสาขาจริงและการมอบหมายพนักงานเดิมเป็นฐาน

สถานะล่าสุด: เผยแพร่ UI ใหม่และการตรวจสิทธิ์ที่ https://bigbcoffeepos-web.vercel.app แล้วเมื่อ 7 กันยายน 2026 ดูขอบเขตที่เสร็จ ผลทดสอบ และงานคงเหลือใน [บันทึกการพัฒนา](UI_REDESIGN_IMPLEMENTATION.md) ส่วนเอกสารนี้เป็นแผนเป้าหมายทั้งระบบ

## 1. ข้อกำหนดที่ยืนยันแล้ว

- ขอบเขตที่ผู้ใช้ยืนยันมี 5 หน่วยงาน ได้แก่ กาแฟวัชรเกียรติ กาแฟพงษ์อนันต์ กาแฟศุภชัย บ่อถ่ายน้ำมันวัชรเกียรติ และบ่อถ่ายน้ำมันพงษ์อนันต์
- กาแฟและบ่อถ่ายน้ำมันที่ใช้ชื่อสถานที่เดียวกันเป็นคนละสาขาในระบบ โดยข้อมูลและสิทธิ์ต้องแยกจากกัน
- ใช้รหัสสาขาและการผูกพนักงานกับสาขาที่มีอยู่เดิมเป็นฐาน โดยรักษาบทบาทและประวัติของแต่ละคนไว้ระหว่างเปลี่ยน UI
- ผู้ใช้เห็นเฉพาะสาขาที่ได้รับสิทธิ์ แม้สองสาขาจะเป็นประเภทร้านเดียวกัน
- พนักงานเปลี่ยนประเภทร้านของสาขาเองไม่ได้
- การรองรับผู้ใช้หลายสาขาเป็นส่วนต่อยอดเมื่อพบความต้องการจริง โดยเริ่มจากการมอบหมายสาขาเดิมที่บันทึกไว้
- ร้านกาแฟใช้หน้าขายเครื่องดื่ม ส่วนบ่อถ่ายน้ำมันใช้หน้ารับรถ ใบงาน อะไหล่ และค่าแรง
- หน้าตาต้องมีเอกลักษณ์ชัดเจน พร้อมรองรับคอมพิวเตอร์ แท็บเล็ต และมือถือ
- การรับเงินหลายวิธียังคงอยู่ในขอบเขต และต้องใช้บัญชีรับเงินกับอุปกรณ์ของสาขาที่กำลังทำรายการ
- แผนนี้แทนข้อเสนอเดิมที่ให้พนักงานสลับชุดร้านทั่วไปได้ โดยตัดร้านอาหาร มินิมาร์ท และบริการทั่วไปออกจากรอบนี้

เริ่มจากแผนและภาพตัวอย่าง แล้วผู้ใช้สั่งให้ลงมือพัฒนาต่อในแอปเดิมเมื่อ 6 กันยายน 2026

### รายชื่อสาขาและพนักงานเดิมที่ตรวจพบ

ตรวจแบบอ่านอย่างเดียวจากฐานข้อมูลที่ `apps/api/.env` ของโปรเจกต์นี้เชื่อมอยู่ โดยอ่านเฉพาะรหัส ชื่อ ประเภทสาขา สถานะ และการมอบหมายของผู้ใช้ที่ยังเปิดใช้งาน

| หน่วยงานตามขอบเขต | รหัสที่พบในฐานนี้ | พนักงานที่ผูกไว้ในฐานนี้ |
| --- | --- | --- |
| กาแฟ วัชรเกียรติ | 1 | จ๋า |
| กาแฟ พงษ์อนันต์ | 2 | กวาง, กฐิน |
| กาแฟ ศุภชัย | 3 | นก |
| บ่อถ่ายน้ำมัน วัชรเกียรติ | 4 | หมู, เผือก, เบิ้ม |
| บ่อถ่ายน้ำมัน พงษ์อนันต์ | 132 — เพิ่มตามคำสั่งผู้ใช้แล้ว | ยังไม่มีพนักงานผูกสาขา |

พนักงานที่ระบุข้างต้นทั้ง 7 คนมีบทบาท `manager` และมี `branchId` อยู่แล้ว จึงต้องใช้สาขาที่ผูกไว้ตรวจสิทธิ์แทนการอนุญาตทุกสาขาจากชื่อบทบาท

บัญชี “ผู้จัดการ” บทบาท `admin` คงสิทธิ์ส่วนกลางตามระบบเดิมและเลือกได้ทุกสาขาที่เปิดใช้งาน ส่วน “แคชเชียร์ 1” และ “แคชเชียร์ 2” ยังไม่มี `branchId` จึงถูกหยุดที่หน้ารอผูกสาขา

ผู้ใช้ยืนยันภายหลังว่ายังไม่ได้สร้างบ่อถ่ายน้ำมันพงษ์อนันต์และให้เพิ่มได้ จึงสร้างในฐานที่แอปใช้อยู่เป็นรหัส 132 และตรวจซ้ำว่าไม่สร้างรายการซ้ำ โดยคงการมอบหมายพนักงานเดิมทุกคน

## 2. สิทธิ์สาขา

สิทธิ์ที่ใช้ตัดสินใจคือ ผู้ใช้ + สาขาที่ได้รับมอบหมาย + งานที่อนุญาต

เริ่มต้นจาก `User.branchId` และ `User.role` ที่มีอยู่ โดยแก้เส้นทางอ่าน/บันทึกให้เคารพการมอบหมายเดิมและไม่กำหนดสาขาพนักงานใหม่ระหว่างออกแบบ

| ผู้ใช้ | สาขาที่เห็น | งานที่ทำได้ |
| --- | --- | --- |
| พนักงานร้านกาแฟ | สาขากาแฟที่ได้รับมอบหมาย | ขายเครื่องดื่ม จัดคิว รับเงิน และเปิด–ปิดกะตามสิทธิ์ |
| พนักงานบ่อถ่ายน้ำมัน | สาขาบ่อถ่ายน้ำมันที่ได้รับมอบหมาย | รับรถ ทำใบงาน เบิกสินค้า บันทึกค่าแรง และรับเงินตามสิทธิ์ |
| ผู้จัดการสาขา | สาขาที่ได้รับมอบหมายเท่านั้น | จัดสินค้า สต็อก รายงาน อนุมัติส่วนลดและคืนเงินตามสิทธิ์ |
| ผู้ดูแลหลายสาขา | เฉพาะรายการสาขาที่ระบุให้เข้าถึง | สลับสาขาและดูรายงานรวมภายในขอบเขตที่ได้รับ |
| ผู้ดูแลระบบ | งานตั้งค่าตามสิทธิ์ที่ระบุ | บทบาทนี้ไม่ทำให้ได้รับสิทธิ์ดูยอดเงินทุกสาขาโดยอัตโนมัติ |

รุ่นที่ลงโค้ดนี้ใช้ `manager` ตามสาขาประจำและคง `admin` เป็นผู้ดูแลส่วนกลางตามระบบเดิม ส่วนการแยกเจ้าของกับผู้ดูแลเฉพาะงานยังต้องออกแบบสิทธิ์เพิ่มก่อนเปลี่ยนบัญชีจริง

ผู้ใช้ที่มีสิทธิ์สาขาเดียวเข้าไปที่หน้างานของตนโดยตรงและเห็นชื่อสาขาคงที่ ส่วนผู้ใช้หลายสาขาเลือกได้เฉพาะสาขาที่ได้รับมอบหมาย

สาขาที่ไม่ได้รับสิทธิ์ต้องไม่ปรากฏในตัวเลือก ผลค้นหา รายงานรวม รายการแจ้งเตือน หรือข้อมูลที่ส่งมาที่เครื่อง

ตรวจสิทธิ์ทุกครั้งที่อ่าน แก้ไข ลบ ส่งออก พิมพ์ รับเงิน และคืนเงิน รวมถึงการเปิด URL หรือเลขบิลโดยตรง

เมื่อเปลี่ยนสาขาต้องเปลี่ยนตะกร้า บิลพัก กะ สินค้า ลูกค้า เครื่องพิมพ์ จอลูกค้า และช่องทางรับเงินพร้อมกัน โดยข้อมูลที่ยังทำไม่เสร็จเก็บแยกตามผู้ใช้และสาขา

เมื่อถูกถอนสิทธิ์ให้หยุดคำขอใหม่และตรวจสิทธิ์อีกครั้งก่อนส่งรายการออฟไลน์ โดยเก็บรายการค้างไว้ให้ผู้มีสิทธิ์ตรวจต่อได้

## 3. ข้อมูลที่แยกต่อสาขา

- สินค้า เมนู ตัวเลือกสินค้า สูตรวัตถุดิบ อะไหล่ ราคาขาย และค่าบริการ
- สต็อก การรับเข้า การเบิกใช้ ประวัติการปรับยอด และเอกสารจัดซื้อ
- ลูกค้า แต้ม ประวัติซื้อ รถ ทะเบียน เลขไมล์ และประวัติการเข้ารับบริการ
- ออเดอร์ ใบงาน บิลพัก ส่วนลด ใบเสร็จ และเอกสารอื่น
- รายการรับเงิน คืนเงิน บัญชีรับเงิน เครื่องรับบัตร กะ และยอดปิดกะ
- พนักงาน สิทธิ์ อุปกรณ์ จอลูกค้า เครื่องพิมพ์ และการเชื่อมต่อภายนอก
- รายงาน ไฟล์ส่งออก ประวัติการทำรายการ คิวส่งข้อมูล และข้อมูลที่เก็บไว้ในเครื่อง

รายการข้อมูลต้องผูกกับสาขาที่แท้จริง และระบบต้องตรวจสาขาของรายการนั้นเองก่อนทำงาน โดยไม่เชื่อเลขสาขาที่หน้าจอส่งมาเพียงอย่างเดียว

รายงานรวมเป็นความสามารถเพิ่มเติมสำหรับผู้มีสิทธิ์หลายสาขา และรวมเฉพาะสาขาที่ได้รับอนุญาต

## 4. ข้อค้นพบก่อนเริ่มพัฒนา

| จุด | หลักฐานที่อ่านพบ | ผลต่อแผน |
| --- | --- | --- |
| ประเภทร้าน | มี `coffee` และ `oil_service` อยู่แล้ว | ใช้สองประเภทนี้เป็นขอบเขตรอบใหม่ |
| การตรวจสาขา | `requireBranchAccess` ยอมให้ `admin` และ `manager` ผ่านทันที | ต้องเปลี่ยนเป็นตรวจการมอบหมายสาขาสำหรับทุกบทบาท |
| รายการสาขา | เส้นทาง `/api/branches` เรียกฟังก์ชันที่คืนสาขาทั้งหมด | ต้องคืนเฉพาะสาขาที่ผู้ใช้มีสิทธิ์ |
| รายการเมนู/ลูกค้า | เส้นทางอ่านเรียก `getMenu()` และ `getCustomers(search)` โดยไม่มีสาขาในคำขอส่วนนี้ | ต้องตรวจและออกแบบขอบเขตข้อมูลให้ครอบคลุมรายการเหล่านี้ |
| ผู้ใช้ | มี `branchId` ในข้อมูลผู้ใช้และ token พร้อมพนักงาน 7 คนที่ผูกสาขาไว้แล้วในฐานที่ตรวจ | ใช้การมอบหมายเดิมก่อน และเพิ่มโครงหลายสาขาเฉพาะเมื่อยืนยันว่าจำเป็น |
| หน้ารับเงิน | QR/บัตร/Wallet ใช้พนักงานยืนยัน | เพิ่มการเชื่อมรับเงินจริงและสถานะที่ตรวจสอบได้ |

หลักฐานภายใน: `apps/api/src/middleware/auth.ts`, `apps/api/src/index.ts`, `apps/api/src/store/branches.ts`, `apps/api/prisma/schema.prisma`, `apps/web/src/contexts/BranchContext.tsx`, `apps/web/src/types.ts`

ตารางนี้บันทึกปัญหาก่อนแก้ ปัจจุบันแก้สิทธิ์และทดสอบคำขอข้ามสาขาแล้วตามบันทึกการพัฒนา

## 5. ภาพลักษณ์ใหม่

ใช้โครงหน้าจอร่วมกัน แต่กำหนดภาพลักษณ์และลำดับงานเฉพาะแต่ละกิจการ

| องค์ประกอบ | ร้านกาแฟ | บ่อถ่ายน้ำมัน |
| --- | --- | --- |
| บุคลิก | อบอุ่น เรียบร้อย มีรายละเอียดของแบรนด์ | ชัดเจน แข็งแรง อ่านสถานะงานเร็ว |
| สีหลัก | เขียวเข้ม `#163D32` | กราไฟต์ `#17212B` |
| สีเน้น | สีส้มอิฐ `#C66C47` | ส้มเข้ม `#D45A20` |
| พื้น | ครีม `#F4F1EB` และขาวอุ่น | เทาอ่อน `#F2F4F6` และขาว |
| ภาพสินค้า | เครื่องดื่ม/เบเกอรีที่จัดแสงและขนาดสม่ำเสมอ | น้ำมันเครื่อง ไส้กรอง และวัสดุที่แยกชนิดง่าย |
| จุดสำคัญ | ชื่อเครื่องดื่ม ตัวเลือก ราคา และคิว | ทะเบียนรถ เลขไมล์ ช่องบริการ สถานะ และยอดใบงาน |

รายละเอียดที่เปลี่ยนจากแบบแรก:

- เพิ่มแถบเมนูที่มีเอกลักษณ์และชื่อกิจการในตำแหน่งชัดเจน
- ใช้ภาพสินค้าจริงหรือภาพประกอบที่มีคุณภาพแทนไอคอนซ้ำทุกการ์ด
- จัดขนาดชื่อหน้า ชื่อสินค้า รายละเอียด และยอดเงินให้เห็นลำดับชัด
- ใช้พื้นที่ว่าง เส้นแบ่ง และพื้นผิวอย่างมีหน้าที่ พร้อมลดกรอบซ้ำซ้อน
- ตะกร้าและใบงานมีรายการสรุปที่อ่านง่าย พร้อมปุ่มรับเงินเป็นจุดเด่นเพียงจุดเดียว
- แสดงสถานะกะ การเชื่อมต่อ และเครื่องพิมพ์อย่างกระชับ โดยเปิดรายละเอียดได้เมื่อจำเป็น
- สีและรูปทรงของปุ่มร่วมกันทั้งระบบ และมีการตอบสนองหลังแตะที่สั้นและชัด

ใช้ IBM Plex Sans Thai สำหรับภาษาไทยและฟอนต์ตัวเลขที่อ่านจำนวนเงินง่าย โดยเนื้อหา 14–16px ช่องกรอกอย่างน้อย 16px และปุ่มหลักสัมผัสได้อย่างน้อย 44×44px

โหมดมืดต้องออกแบบสีของพื้น ข้อความ และสถานะแยกชุด พร้อมตรวจความต่างสีและการใช้งานด้วยแป้นพิมพ์ก่อนเปิดใช้

อ้างอิงเกณฑ์ความอ่านง่าย: [W3C Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C Target Size Enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

## 6. หน้างานของร้านกาแฟ

ขั้นตอนหลัก: เลือกเครื่องดื่ม → ปรับขนาด/ความหวาน/ส่วนเพิ่ม → รับเงิน → ส่งคิว → ส่งมอบ

- หน้าขายมีหมวดสินค้า รูป ราคา ค้นหา รายการขายบ่อย และบาร์โค้ดตามการใช้งาน
- ตัวเลือกเครื่องดื่มเปิดในแผงเดียว พร้อมเห็นราคาที่เปลี่ยนก่อนเพิ่มเข้าบิล
- ตะกร้าแก้จำนวน ตัวเลือก หมายเหตุ สมาชิก และส่วนลดจากรายการที่เกี่ยวข้อง
- คิวบาริสต้าแสดงรอทำ กำลังทำ และพร้อมรับ พร้อมหมายเหตุเครื่องดื่มอ่านได้ชัด
- สต็อกแสดงวัตถุดิบ สูตร แก้ว ฝา และวัสดุที่ร้านใช้จริง
- ใบเสร็จ สติกเกอร์ และจอลูกค้าใช้ชื่อร้านกับอุปกรณ์ของสาขานั้น

## 7. หน้างานของบ่อถ่ายน้ำมัน

ขั้นตอนหลัก: รับรถ → บันทึกทะเบียน/เลขไมล์ → เลือกสินค้าและบริการ → จัดช่องบริการ/ช่าง → ทำงาน → ตรวจรายการ → รับเงิน → ส่งมอบ

- หน้าแรกของงานขายเน้นรถที่กำลังรับบริการและใบงานที่ยังเปิด
- ใบงานแสดงลูกค้า รถ ทะเบียน เลขไมล์ วันที่ ผู้รับงาน ช่าง และช่องบริการ
- แยกรายการน้ำมันเครื่อง ไส้กรอง อะไหล่ ค่าแรง และบริการอื่นในบิลอย่างอ่านง่าย
- เลือกเกรดน้ำมัน ปริมาณ หน่วย และราคาตามรายการที่สาขาตั้งไว้ โดยไม่คาดเดาความเหมาะสมกับรถเอง
- สถานะใบงานประกอบด้วยรอเข้าช่อง กำลังทำ รอตรวจ รอชำระ และส่งมอบ
- ประวัติรถและการนัดครั้งถัดไปอยู่ในขอบเขตสาขาที่มีสิทธิ์
- ยืนยันกับพนักงานเรื่องการเบิกน้ำมันเป็นขวดหรือลิตร และจุดที่ตัดสต็อกก่อนพัฒนาจริง

หน้าตัวอย่างสามารถแสดงขั้นตอนและข้อมูลจำลองเหล่านี้ได้ แต่ระบบใบงาน รถ เลขไมล์ และช่องบริการต้องประเมินโครงข้อมูลจากงานจริงก่อนลงรายละเอียดพัฒนา

## 8. หลังร้านและอุปกรณ์

เมนูร่วมประกอบด้วย สินค้า/สต็อก ลูกค้า พนักงาน/กะ การเงิน/รายงาน และตั้งค่าสาขา โดยแต่ละบทบาทเห็นเฉพาะงานที่ได้รับอนุญาต

คอมพิวเตอร์ใช้เมนูด้านซ้าย พื้นงานตรงกลาง และตะกร้าหรือใบงานด้านขวา; แท็บเล็ตย่อเมนูเมื่อพื้นที่ไม่พอ; มือถือแสดงหน้างานกับหน้ารับเงินคนละขั้นโดยเก็บข้อมูลเดิมไว้

จอครัวใช้เฉพาะกาแฟ ส่วนจอบริการใช้ใบงานและช่องบริการของบ่อถ่ายน้ำมัน และจอลูกค้าจับคู่กับเครื่องขายเฉพาะเครื่อง

เครื่องพิมพ์ ใบเสร็จ ลิ้นชักเงิน และเครื่องรับบัตรต้องตรวจเป็นรายรุ่นและวิธีเชื่อมต่อ โดยรองรับหน้าจอได้ไม่ได้หมายความว่าอุปกรณ์ต่อพ่วงทุกชนิดใช้ได้ทันที

## 9. การรับเงิน

รองรับเงินสด QR PromptPay โอนเงิน บัตร E-Wallet และการจ่ายหลายวิธีในบิลเดียว โดยทุกวิธีผูกกับสาขาและบิลที่ถูกต้อง

- เงินสดแสดงยอดรับ เงินทอน และผลต่อยอดกะ
- QR แสดงยอดบิลและเวลาหมดอายุ พร้อมตรวจผลยืนยันจากผู้ให้บริการทางระบบ
- โอนเงินแยกสถานะพนักงานตรวจยอดออกจากการยืนยันโดยผู้ให้บริการ
- บัตรและ Wallet แสดงเฉพาะช่องทางที่สาขาเปิดใช้และเชื่อมต่อได้จริง
- แบ่งจ่ายแสดงรายการรับเงิน ยอดจ่ายแล้ว และยอดคงเหลือ พร้อมรักษารายการที่รับเงินสำเร็จไปแล้ว
- การคืนเงินต้องตรวจสิทธิ์ผู้ใช้กับสาขาของบิล พร้อมแสดงสถานะและเก็บหลักฐาน
- รายการซ้ำหรือผลแจ้งซ้ำต้องไม่รับเงิน ตัดสต็อก เพิ่มแต้ม หรือสร้างบิลซ้ำ
- หากรับเงินจริงสำเร็จแต่บันทึกบิลไม่สำเร็จ ต้องเก็บงานให้ตรวจและกู้คืนได้
- โหมดออฟไลน์เริ่มจากเงินสดตามสิทธิ์ร้าน และแยกสถานะรับเงินออกจากสถานะส่งข้อมูล
- คำนวณเงินด้วยหน่วยสตางค์หรือชนิดทศนิยมที่แม่นยำ และแยกยอด QR/บัตร/Wallet/โอนตอนปิดกะ

เริ่มเชื่อมผู้ให้บริการหนึ่งรายหลังยืนยันบัญชีและอุปกรณ์ของแต่ละสาขา โดยยังไม่เลือกผู้ให้บริการแทนร้าน

ตัวอย่าง [Omise PromptPay](https://docs.omise.co/promptpay) ใช้ผลแจ้งชำระเงินและการตรวจสถานะกลับจากระบบ พร้อมมีข้อจำกัดการคืนเงินผ่านบริการที่ต้องตรวจเมื่อเลือกใช้จริง

## 11. การตรวจรับและการย้อนกลับ

ทดสอบครบกาแฟ 3 สาขาและบ่อถ่ายน้ำมัน 2 สาขาตามรายการจริง โดยใช้สำเนาข้อมูลในระบบทดสอบหลังจับคู่ข้อมูลเดิมครบ

ต้องตรวจกรณีกาแฟวัชรเกียรติเปิดข้อมูลกาแฟพงษ์อนันต์ กรณีกาแฟวัชรเกียรติเปิดข้อมูลบ่อถ่ายน้ำมันวัชรเกียรติ และกรณีบ่อถ่ายน้ำมันวัชรเกียรติเปิดข้อมูลบ่อถ่ายน้ำมันพงษ์อนันต์ เพื่อให้การแยกครอบคลุมทั้งประเภทร้านและสถานที่

ทดสอบพนักงานแต่ละสาขา ผู้จัดการสาขาเดียว ผู้มีสิทธิ์สองสาขา และผู้ถูกถอนสิทธิ์ โดยตรวจทั้งหน้าจอและคำขอเข้าใช้ข้อมูลโดยตรง

ตรวจรายการเมนู ลูกค้า สต็อก บิล รายงาน ส่งออก คืนเงิน จอลูกค้า บิลพัก ข้อมูลในเครื่อง และคิวออฟไลน์ให้ครอบคลุมการข้ามสาขา

ทดสอบเน็ตหลุดหลังเงินเข้า กดรับเงินซ้ำ ชำระบางส่วน ผลแจ้งซ้ำ สต็อกชิ้นสุดท้ายจากสองเครื่อง และพิมพ์ไม่สำเร็จ

ทดสอบหน้าจอ 360–1440px โหมดสว่าง/มืด การขยายตัวอักษร และแป้นพิมพ์บนจอ โดยปุ่มรับเงินและข้อมูลจำเป็นต้องไม่ถูกบัง

เปิด UI ใหม่ทีละสาขาและเก็บทางกลับ UI เดิมที่ยังผ่านการตรวจสิทธิ์ใหม่ โดยไม่ย้อนกลับไปใช้กติกาที่เปิดข้อมูลข้ามสาขา

การปรับโครงข้อมูลต้องเก็บประวัติบิลเดิมและมีแผนย้ายข้อมูลทดสอบก่อนลงจริง โดยหยุดขออนุมัติก่อนการลบข้อมูลถาวรตามกฎโครงการ

ข้อมูลลูกค้า/สินค้าที่เคยใช้ร่วมกันต้องระบุเจ้าของสาขาก่อนย้าย โดยไม่แจกข้อมูลให้ทุกสาขาเป็นค่าเริ่มต้น

## 12. สถานะการส่งมอบรอบนี้

- แก้แผนให้ตรงร้านกาแฟ/บ่อถ่ายน้ำมันและการแยกสาขาตามสิทธิ์
- เพิ่มชื่อจริงครบ 5 หน่วยงานตามที่ผู้ใช้ยืนยัน พร้อมผลอ่านฐานข้อมูลที่พบ 4 สาขาและพนักงานที่ผูกสาขา 7 คน โดยไม่แก้ข้อมูลในฐาน
- ภาพตัวอย่างก่อนหน้านี้แสดงตัวแทนกิจการสองประเภท โดยชื่อสาขาและบุคคลในหน้าพัฒนาจริงต้องใช้รายการเดิมที่ตรวจได้ตามตารางด้านบน
- ผลตรวจของภาพตัวอย่างฉบับก่อนหน้าใช้รับรองได้เฉพาะฉบับก่อนหน้า
- ภาพตัวอย่างใหม่ใช้ข้อมูลและบทบาทจำลอง โดยไม่ใช่หลักฐานว่าระบบหลังบ้านป้องกันการเข้าถึงข้ามสาขาแล้ว
- ตัวอย่างใหม่ผ่านการตรวจ 360, 736 และ 1024px ทั้งสองประเภทร้านและทั้งสองโหมดสี รวม 12 รูปแบบ โดยไม่ล้นแนวนอน
- ผ่านการทดสอบตัวเลือกสาขาตามบทบาทจำลอง การแยกข้อความสินค้า ตะกร้าแต่ละสาขา การคงข้อมูลรถเมื่อสลับสาขา หน้าคิว/สินค้า/ยอดสาขา พักบิล เงินทอน แบ่งจ่าย และหน้ารับเงินมือถือ
- เบราว์เซอร์ไม่พบข้อผิดพลาด JavaScript ระหว่างการตรวจดังกล่าว และไฟล์ตัวอย่างผ่านการตรวจรูปแบบไฟล์กับ `git diff --check`
- ฉบับส่งมอบใช้รูปแบบที่ผ่านการตรวจ 12 รูปแบบแล้ว โดยคืนการปรับความสูงทดลองที่ยังตรวจไม่ครบหลังระบบอนุมัติอัตโนมัติปฏิเสธการเปิดตัวทดสอบใหม่เนื่องจากสิทธิ์เข้าสู่ระบบถูกเพิกถอน
